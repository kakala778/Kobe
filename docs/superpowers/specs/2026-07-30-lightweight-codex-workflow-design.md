# 轻量 Superpowers Codex 工作流设计

> 日期：2026-07-30  
> 状态：设计已在对话中批准，等待用户审阅本文档  
> 适用对象：使用 Codex Desktop 学习 Vibe Coding 的零基础用户

## 1. 目标

建立一套“简单任务保持轻松、复杂任务自动加强”的 Codex 工作流。

这套工作流需要同时做到：

- 保留 Vibe Coding 的快速反馈和低门槛；
- 在错误、复杂功能和高风险操作中提供可靠的工程保护；
- 自动判断任务规模，减少用户反复选择流程；
- 允许用户用一句话覆盖自动判断；
- 不因为安装了 Superpowers，就让每个文字或样式修改都进入完整工程流程。

## 2. 已确认的选择

- 工作流强度：轻量模式；
- 分级方式：Codex 自动判断，用户可以随时覆盖；
- 安全底线：系统调试与完成前验证始终保留；
- 首次试用：等待下一次真实任务，不创建练习项目；
- 当前作品集：不因为配置工作流而修改网页功能；
- GitHub：读取可以直接进行，写入前继续询问。

## 3. 自动分级规则

### 3.1 简单任务

符合以下特征时，默认使用轻量流程：

- 修改文字、颜色、间距或图片说明；
- 小范围调整一个现有行为；
- 修复能够清楚定位的低风险问题；
- 通常只影响一到两个文件；
- 不新增依赖，不改变数据结构，不涉及外部系统。

流程：

1. 确认目标；
2. 查看相关文件；
3. 小范围修改；
4. 运行与改动匹配的检查；
5. 汇报改动和验证结果。

简单任务不强制创建设计文档、实施计划、Git worktree 或完整 TDD 流程。

### 3.2 中等任务

符合以下特征时，先做简短需求确认，再决定是否升级：

- 新增一个小功能；
- 修改多个互相关联的页面区域；
- 影响两到三个文件；
- 存在不止一种合理实现方式；
- 需要新增一项有限依赖。

流程：

1. 简短确认需求与完成标准；
2. 比较必要的实现选择；
3. 实现；
4. 为重要行为增加测试或可重复检查；
5. 完成前运行验证。

### 3.3 复杂或高风险任务

出现以下任一情况时，默认启用完整流程：

- 多文件功能或结构调整；
- 新框架、新服务或重要依赖；
- 登录、权限、用户数据、支付或数据库；
- 部署、生产环境、域名或云端资源；
- 向 GitHub 推送，或创建、修改 Issue、Pull Request、评论等远程内容；
- 难以回滚的操作；
- 多个实施阶段或多个独立子任务。

流程：

1. `brainstorming`：澄清需求、比较方案并取得设计批准；
2. `writing-plans`：形成可执行的实施计划；
3. 当改动跨多个文件、包含多个阶段，并且需要保护当前稳定分支时，使用 `using-git-worktrees` 隔离功能；
4. `test-driven-development`：先建立失败检查，再实现；
5. 已有获批计划时可以使用 `executing-plans`；至少有两个互不依赖的任务时，才使用并行协作 Skill；
6. `requesting-code-review`：对较大改动做审查；
7. `verification-before-completion`：运行完整验证；
8. 外部写入前取得用户同意。

## 4. 不可省略的安全底线

### 4.1 错误必须先定位

出现错误、测试失败或异常行为时，使用 `systematic-debugging`：

1. 稳定复现；
2. 收集错误文本、日志和环境信息；
3. 找出根因；
4. 建立能够暴露问题的检查；
5. 做最小修复；
6. 再次运行验证。

禁止在没有证据的情况下连续猜测和反复修改。

### 4.2 完成必须有新证据

宣布“完成”“修好了”或“测试通过”前，使用 `verification-before-completion`：

- 明确什么命令或操作能够证明结论；
- 在当前任务中重新运行完整检查；
- 阅读退出码、失败数和关键输出；
- 只根据刚得到的证据汇报状态。

## 5. Skill 分层

### 5.1 自动使用

- `using-superpowers`
- `systematic-debugging`
- `verification-before-completion`

### 5.2 按任务条件使用

- `brainstorming`
- `writing-plans`
- `test-driven-development`
- `requesting-code-review`
- `receiving-code-review`

### 5.3 较少使用

- `using-git-worktrees`
- `executing-plans`
- `subagent-driven-development`
- `dispatching-parallel-agents`
- `finishing-a-development-branch`
- `writing-skills`

不会为了“显得专业”而调用较重的 Skill。只有当任务结构确实满足触发条件时才使用。

## 6. 其他已安装能力的职责

### Playwright

用于真实浏览器验收：

- 打开本地或指定网页；
- 获取页面快照；
- 点击、填写和刷新；
- 检查控制台与网络请求；
- 测试桌面端与手机宽度；
- 在需要时保存截图或追踪。

首次执行浏览器 `open` 时可能下载浏览器组件，需要单独记录下载和磁盘变化。

### Frontend App Builder

仅用于：

- 创建新的视觉型前端项目；
- 新建重要页面或组件；
- 明确要求重新设计或现代化界面。

普通文案、颜色和间距调整不触发它。

### GitHub Plugin

用于：

- 读取仓库、Issue、Pull Request 和 CI 状态；
- 需要时准备提交、分支或 PR；
- 排查 GitHub Actions。

权限保持“写入前询问”。读取可以直接执行，评论、创建 Issue、推送、合并等写入必须先取得用户同意。

## 7. 用户覆盖语句

用户可以随时使用以下短句覆盖自动分级：

- `这次简化流程`
- `这次使用完整流程`
- `先只分析，不修改`
- `不要安装依赖`
- `不要提交或推送`
- `只修改这些文件：……`
- `完成后先给我看 diff`

最新、最明确的用户指令优先。

## 8. 上下文与权限

- 每次任务开始时，先确认当前目录、仓库状态和适用 Skill；
- 只读取与任务有关的文件，避免无目的地加载整个项目；
- 长任务在关键阶段更新计划；
- 需求或方向发生变化时，先更新当前理解；
- 不把临时试验、浏览器产物或依赖写入项目，除非任务需要；
- 不把本地完成误报为已经推送或部署；
- 不自动扩大外部账号、GitHub 或云服务权限。

## 9. 验证策略

验证强度与风险匹配：

| 改动类型 | 最低验证 |
|---|---|
| 文案 | 检查目标文本和 Git diff |
| HTML/CSS | 语法或结构检查，加浏览器视觉检查 |
| JavaScript 行为 | 可重复的行为检查，加浏览器交互 |
| Bug 修复 | 复现失败、修复后通过、相关回归检查 |
| 新依赖 | 安装结果、版本、锁文件和基础运行 |
| 部署 | 构建成功、部署状态、生产地址和关键页面 |
| GitHub 写入 | 本地状态、目标仓库/分支、写入后的远程状态 |

## 10. 首次真实任务验收

不创建专门练习项目。下一次真实任务到来时观察：

1. Codex 是否正确判断简单、中等或复杂；
2. 简单任务是否保持短流程；
3. 出错时是否先定位根因；
4. 完成前是否给出新验证证据；
5. 是否避免不必要的 worktree、Agent、计划或依赖；
6. 外部写入前是否征求同意；
7. 用户能否用一句覆盖语句改变流程。

任务结束后记录：

- 哪些步骤确实减少返工；
- 哪些步骤显得多余；
- 自动分级是否准确；
- 下一轮需要保留、简化或加强的规则。

## 11. 持久化方案

设计获最终审阅后，再制定实施计划。推荐实施方式：

1. 在用户级 `C:\Users\iq\.codex\AGENTS.md` 中加入简短的轻量模式规则，使其适用于所有项目；
2. 保留各项目自己的 `AGENTS.md`，用于项目命令、文件范围和验证要求；
3. 不复制或修改 Superpowers 自带 Skill；
4. 不改 Codex 内部插件缓存；
5. 为全局规则保留清晰的开始和结束标记，方便以后更新或删除；
6. 配置后用下一次真实任务验证，再根据实际体验迭代。

## 12. 回滚

如果轻量模式不合适：

- 删除用户级 `AGENTS.md` 中对应的轻量模式区块；
- 不需要卸载 Superpowers；
- 不影响作品集代码或 Git 历史；
- 如决定完全停用，再通过 Codex Plugins 页面卸载 Superpowers。
